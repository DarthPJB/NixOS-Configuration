## Scope

This review targets the **Nix-based CI pipeline generator** currently living in:
- `ci.nix` (316 lines) — CI module: machine registries, job definitions, GitHub Actions struct
- `ci/generate-workflow.nix` (103 lines) — Pipeline: Nix eval → JSON → PyYAML → YAML
- `flake.nix` (L217-374) — Flake wiring: `generate-ci-workflow`, `validate-ci-workflow`, `ci` apps
- `.github/workflows/ci.yml` (166 lines) — Generated output: 5 jobs across 15 machines on self-hosted runners

## Two Objectives

### Objective 1: Ketchup Readiness
Assess the CI pipeline generator for extraction into the **Ketchup** open-source toolkit. The topology engine (`lib/topology_library.nix`) already demonstrates the pattern: generic engine functions imported by proprietary data. Can the CI generator follow the same model?

Key questions:
- What is generic/reusable vs Bargman-proprietary?
- Can we create `lib/ci_library.nix` as a clean API boundary?
- Does the generation pipeline (Nix → JSON → YAML) generalise beyond GitHub Actions?
- What refactoring is needed, and what is the risk of breaking golden output?

### Objective 2: Parallelism Control
Determine if per-job Nix build parallelism settings can be added to the CI generator. The goal: **x86_64 builds can be parallelised; aarch64 builds cannot** (or must be severely constrained to avoid RPi OOM).

Key questions:
- Can we inject `--option max-jobs N --option cores N` per CI job?
- How should settings flow: flake → ci.nix → generated workflow → nix build?
- Can this be done without breaking the current CI output?
- Is there a path to complex per-machine tuning (in-flake expressions)?
