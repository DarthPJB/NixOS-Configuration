## Ground 2 — Suggested cleanup candidates
Proposed cleanup actions are grouped by priority. Evidence shows that these files are either unused, outdated, or duplicate newer systems, so removing or archiving them will reduce cognitive load and risk of stale operations.

- **High**
  - `documentation/2026-07-18-MULTI-HORIZON-GATEWAY-PLAN.md` references `topology/<machine>.json`, `topology/shared.json`, and `real-topology/golden/*.json` as the editing workflow (`lines 14-23`, `174-235`, `370-381`, `533-600`), yet the repository now only contains `topology/shared.nix`, `topology/cortex-alpha.nix`, and `topology/default.nix`. The instructions literally point to files that no longer exist and describe editing JSON instead of the live `.nix` data; archive or rewrite the plan to reference the current `.nix` source (or move it to an historical folder) before the next reviewer acts on it.
  - `server_services/hedgedoc.nix` defines a full nginx/hedgedoc stack for `hedgedoc.johnbargman.com` (`lines 1-37`) but nothing imports it (`grep -R "hedgedoc.nix"` returns no usages outside its own file). The block sits idle and drags undispatched topology work along for no reason; delete it or reframe it as documentation so it is clear that no machine is currently responsible for this host.
- **Medium**
  - `snippets/syncthing_server.nix` contains a commented-out `services.nginx` block (`lines 35-46`) plus plaintext placeholders (`lines 105-157`) but is not imported anywhere in the tree (`grep -R "syncthing_server.nix"` does not hit any module). It is dead code that also carries credentials / absolute mount scripts; remove it or turn it into safe documentation to avoid accidental reuse.
  - `snippets/enable-wg.nix` used to be the legacy WireGuard client module (`lines 1-81`), but every import of that file has been replaced by `modules/enable-wg-topology.nix` (the only references now are in documentation). Delete/archive this snippet so it no longer competes with the working topology-driven module.
  - `snippets/obs-box.nix` and `snippets/local-worker.nix` appear to be retired machine configs (the only references are in `documentation/2026-07-20-REVIEW/tpol-minimax-REVIEW-2026-07-20.md:214-215`). No `import` statements point at them, so they add noise without value; move them to a dedicated `archive/` folder or delete them.
  - `snippets/grafana-deprecated/disk-usage.json` and `failstate-overview.json` are referenced only by legacy dashboard reviews (`documentation/2026-07-11-GRAFANA-DASHBOARD-REVIEW/...`), never by deployment code, and sit in the active `snippets/` tree. Archive or delete these JSON dumps so the repository mirrors only the dashboards that are actually loaded into Grafana.
  - `lib/topology/mkBackupSettings.nix` / `lib/topology/genBackup.nix` are not wired anywhere (no calls from `modules/core-router-topology.nix`) and the topology data does not contain a `backup` section (search `grep -R "backup" topology/cortex-alpha.nix` returns nothing). The transformer emits an empty `machines` attrset and never contributes to a module; either delete until backup plans exist or extend the topology and wiring simultaneously to avoid untestable scaffolding.

## Ground 3 — Practical issues, risks, and nits
- **Risk** – `machines/remote-worker/default.nix:43-85` defines `services.nginx.virtualHosts` for `johnbargman.*` plus `johnbargman.com-wg`, and `flake.nix:622-652` defines a second `services.nginx` block (csfinancialconsulting.com / csfincon.us / carmel-staging). Those two fragments merge via `lib.mkMerge` but live in different files, each with hardcoded `listenAddresses` (e.g., `193.16.42.101`, `10.0.1.42`, `10.88.127.50`). Managing the same domain names (duplicate `johnbargman.net`) across multiple modules requires edits in two places and defeats the stated topology-first philosophy; unify the definitions (preferably via a single module or topology entry) to keep ACME/port behavior deterministic and avoid drift between `flake` overrides and machine-local blocks.
- **Risk** – `documentation/2026-07-18-MULTI-HORIZON-GATEWAY-PLAN.md` still describes editing `topology/<machine>.json`/`real-topology/golden/*.json` and assumes JSON-based transformers (`lines 14-25`, `174-236`, `370-381`, `533-600`). The actual tree uses `.nix` (see `topology/` contents), so following the plan leads to dead paths. The documentation is actively misleading and should be rewritten or retired before any engineer attempts to follow Phase B instructions.
- **Risk** – `AGENTS.md:212-253` states that `core-router-topology.nix` is “not yet wired into cortex-alpha,” yet `machines/cortex-alpha/default.nix:15-28` already imports that module. Golden-test flows documented in AGENTS implicitly assume the production path is the only active module, so the statement is now stale and encourages skipping validation of the WIP two-layer path even though it is live; update AGENTS and the checkpoints so reviewers know the new module is wired and must pass `nix run .#check-network -- cortex-alpha` before further modifications.
- **Nit** – `snippets/test-new-architecture.nix:9-23` hardcodes `self = { outPath = "/speed-storage/repo/DarthPJB/NixOS-Configuration"; }` when importing `topology/cortex-alpha.nix`. Any attempt to run this test outside that exact path (e.g., this review tree) fails immediately because the path no longer exists. Parameterize or remove the hardcoded outPath so the validation harness can be run from arbitrary clones.
